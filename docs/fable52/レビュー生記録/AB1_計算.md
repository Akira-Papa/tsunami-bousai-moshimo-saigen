### 中-1　内陸（二段計算）の「細かい計算が起きる前」の進みが、遅い端末で大きく落ちる
- 場所：src/main.js:1112（`st.acc` の上限）、1124（`want`）
- 何が起きるか：持ち越し時間 `st.acc` の上限が `st.maxSteps * solver.dt * 1.5 + outerSolver.dt`（細かい計算の dt 基準）で、細かい計算が眠っている間（広い計算だけを進める間）もこの上限がかかる。変更前は、この間の1コマの予算が `min(speed·rdt, maxSteps·6·outer.dt)` で、細かい計算の dt の約6×(outer.dt/inner.dt) 倍まで進めていた。
  - 名古屋駅の近く（n=512）の実測の dt は、細かい計算 0.0346秒・広い計算 0.178秒。上限は maxSteps=48 で 1コマ 2.67秒、maxSteps=2 で 0.28秒。
  - fps が 28 を切ると `st.maxSteps` は 0.8 倍ずつ 2 まで下がる（main.js:1179）。maxSteps=2・20fps で実効 ×5.6（変更前の同じ条件は `min(3, 2·6·0.178)=2.14秒/コマ` で ×43）。内陸の1回は計算の時計で約5050秒、細かい計算が起きるのはその後半（名古屋駅の近くでは、下の測定で4900秒まで眠ったまま＝ほぼ全部の時間がこの状態）なので、遅い端末では再現が15分以上かかり、「止まっている」と受け取られうる（端末での実測はしていない）。
  - 速さ「最速」でも、眠っている間は 1コマ 2.67秒までで、変更前（999/60≒16.6秒）の約1/6。実測：最速・20fps で 2600秒進めるのに 1415コマ（1コマ平均 1.84秒、制御点の待ちを含む）。
- 根拠：コード（上の2行）と、下の「測定」の dt・コマ数。
- 直し方の案：上限を「いま進める側の dt」で決める。例 `const dtLead = outerSolver && !st.innerActive ? outerSolver.dt : solver.dt; const cap = (outerSolver && !st.innerActive ? st.maxSteps * 6 : st.maxSteps) * dtLead * 1.5;`。決定論には影響しない（区切りは sub-step 番号で決まるため）。

### 中-2　表示用の aux（泡・濁り・飛沫）が「step() の呼び出しごと」に走るため、二段計算の追いかけ中は広い計算の1歩ごとに走る（重さ）
- 場所：src/sim/swe.js:615–620（step() の最後の aux）、src/main.js:1132–1138（guard ループで `outerSolver.step(1, 0)`）
- 何が起きるか：二段計算で細かい計算が起きた後は、広い計算を1歩ずつ進めるので、広い計算（768²）の aux が1コマに十数回、細かい計算の aux も同じ回数走る（変更前は1コマ1回ずつ）。aux は NN 全セルで隣4つの双一次補間＋壁・乾き判定を読むので、1回の重さは1歩（2 dispatch）の半分程度と見込む（推測）。加えて `renderer.compute` の呼び出し（＝submit）が1コマ数十回になる。計算の結果には影響しない（aux の出力 T・P・V は計算へ戻らない）が、fps が下がる → maxSteps が下がる → 実効の速さが下がる、の順で効く。表示の側でも、泡・濁りの半ラグランジュ移流が dt の小さい回数の多い補間になり、数値拡散でぼけが増える（見た目のみ）。
- 根拠：コード。重さの実測は下の「測定」の bench を参照（測れた範囲）。
- 直し方の案：aux を step() から外し、1コマ1回 `solver.afterFrame(advancedSeconds)` のような関数で呼ぶ（uFrame.x にそのコマで進んだ計算時間を入れる）。aux は計算へ戻らないので決定論は崩れない。

### 中-3　制御点の読み戻しに「上限時間」がない。control() の中で同期的な例外が出ると、計算が黙って止まったままになる
- 場所：src/sim/swe.js:599（`if (!ctrlBusy) control(); break;`）、629–658（control()）
- 何が起きるか：`ctrlBusy = true` の後、`renderer.compute(ctrlReset/ctrlProbe/ctrlFrontProbe)` で同期的に例外が出ると（パイプラインの生成失敗など）、Promise に入らないので `finally` が走らず、`ctrlBusy` が true のまま残る。以後 step() は制御点で毎回 break して 0 を返し、再生ボタンは「再生中」のまま時計が進まない。画面に何も出ない。
  - 読み戻しが失敗・デバイスロストの場合は、mapAsync が reject → catch → finally で `ctrlDone = at` になり、gain を直さずに先へ進む（止まらない）。これは確かめた（コード）。デバイスロスト後は three.js 側で compute 自体が無効（Renderer.js `_isDeviceLost`）なので、そもそも絵も止まる。
  - mapAsync が決着しない実装があれば、同じく永久に待つ（推測。Chrome では reject される）。
- 根拠：コード。実機で例外を起こす測定はしていない。
- 直し方の案：control() の本体を try/catch で包み、同期例外でも `ctrlBusy=false; ctrlDone=at` にする。あわせて、制御点で待った実時間が一定（例 2秒）を超えたら、gain を直さずに進めて `console.warn` を出す（待ちを無限にしない）。「直さずに進めた」回数を結果画面の計算条件に出せば、決定論が崩れたことも分かる。

### 中-4　T5（同じ結果の試験）は「決定論」を緩い幅でしか試しておらず、アプリの進め方（main.js）・破堤・家屋流失・二段計算を通っていない

## 確かめたが問題なかった点

### A. 決定論（コードを追った結果）
- **uWave**：sub-step 番号が CH の倍数の所でだけ `etaTarget((nSub + CH/2)·dt)` に更新（swe.js:598–601）。1回の呼び出しは CH の区切りを越えない（`m = min(steps−done, CH − nSub%CH)`）ので、どう分けて呼んでも同じ番号で同じ値になる。three.js の uniform は objectGroup（updateType OBJECT）で `renderer.compute()` 1回ごとに書き込まれ、compute 1回ごとに submit される（WebGPUBackend.finishCompute）ので、途中で値を変えても次の dispatch から正しく効く（node_modules/three 0.186 で確認）。
- **最大・到達・破堤・家屋流失**：nSub が CHK の倍数の所だけ（CHK は CH の倍数、CTRL は CHK の倍数）。区切りを必ず踏む。uClock も同じ時刻。
- **gain**：制御点（CTRL の倍数）で ctrlProbe → 読み戻しが届くまで step() はその点から進まない（`ctrlDone !== nSub` で break）。読み戻しのコピーは probe の直後に同期的に submit される（WebGPUAttributeUtils.getArrayBufferAsync は最初の await の前に copyBufferToBuffer を submit）ので、読む値は「その番号の状態」に固定される。和は uint の原子加算（+0.5 の四捨五入つき）で順序に依らない。
- **aux が計算に戻る経路**：なし。stage1/2 が読むのは A・B・S・W と uPrm・uWave（nest では広い計算の A・S）。T0/T1・R・R2・P・V・FM・FV は計算に戻らない。S を書き換えるのは breachKernel と washApply だけで、どちらも CHK の区切り。washApply が書く S.w は frontProbe／ctrlFrontProbe（＝細かい計算を起こす判定）に効くが、これも区切りの上。
- **表示用の読み戻し（coastUpdate）**：別のバッファ（coastSum／coastMax／frontMin と rbC/rbF/rbS/rbB/rbW）で、control() の ctrlSum／ctrlFront・rbCS／rbCF とは共有しない。互いを壊さない。coast.front は「おまかせ」と HUD だけに使われ、計算に戻らない（main.js を grep で確認）。
- **innerActive**：`coast.ctrlFront` は制御点の読み戻しでしか変わらず、その時点で広い計算は制御点で止まっている（finally で ctrlDone が入るのは同じマイクロタスク列の中で、次のコマより前）。したがって次のコマの冒頭で判定すると、起きる時刻は常に「その制御点」になる。`solver.idle(outerSolver.time)` も同じ値。
- **二段の組み合わせ**：広い計算が1歩先行し、細かい計算が `gap = round((To − Ti)/dt_i)` まで追う。細かい計算が途中で止まっても（left 切れ・待ち）、次のコマで同じ広い計算の状態を読みながら続きを進めるので、どう分けても同じ。
- **idle()**：nSub = round(T/dt) で時刻を sub-step 番号に合わせる。T は上の通り決定的。
- **compileAll()**：dt=0 で stage を回し（水は動かない）、maxKernel は時計0で回る。t=0 に 5mm〜1cm の水があるセルの到達が 0 になるのは変更前（aux）と同じ。最後に nSub=0。uWave は保存して戻している。
- **地点の選び直し**：dispose() で dead=true、制御の読み戻しが後から届いても何もしない。新しく足したバッファ（FM・FV・ctrlSum・ctrlFront）・kernel（maxKernel・markUpdate・ctrl*）・読み戻し（rbCS・rbCF）はすべて dispose の一覧に入っている。world の marks（Mesh）は world.dispose の traverse で解放される。
- **一時停止・結果画面の後**：st.playing=false の間は step() を呼ばない。保留中の制御の読み戻しはそのまま届いて片づく。結果画面の後に再生しても、制御の窓（`tAt < pre+rise+hold`）の外なので gain は変わらず、15秒ごとの待ちだけが続く。
- **×1**：持ち越し（st.acc）で、×1 が本当に×1 になる。**最速（999）**：st.acc の上限で1コマ maxSteps 歩まで。

### C. 制御則
- 式は変更前と同じ（err の定義、下げ 0.012/s・上げ 0.004/s、上がる途中は上げない、1回の変化 ±0.6 で打ち切り、gain 0.25〜1.3）。dts は「前回届いてから今回届くまでの計算時間（上限60秒）」から「CTRL·dt（≒15秒、固定）」に変わった。shape() と rising の判定は「届いた時刻」から「読んだ時刻」に変わり、こちらの方が正しい。1回の変化は最大で下げ 0.18×0.6＝−10.8%、上げ +3.6%（上限 0.3 に届かない）。
- 15秒の区切りが粗すぎないか：連続時間で見れば、比例積分の速さ k=0.012/s と、沖から岸まで波が届く遅れ τ（60〜120秒）で kτ≒0.7〜1.4（π/2 未満で安定、ただし減衰は弱い）。15秒の区切りは実効の遅れを約7.5秒増やすだけで、kτ を 5〜10% 悪くする程度。簡単な模型（岸の平均＝遅れ τ・時定数20秒の一次遅れ × gain、τ=40/80/120秒、増幅1.6/2.0）で、2秒ごと（変更前の ×20）・6秒ごと（×60）・15秒ごと（変更後）を比べると、保持中の gain の最小・岸の平均の最大・最小の差は 1% 未満だった（模型での推測。scratchpad の ctl.mjs）。実際の記録でも gain は 1100秒 0.614（前 0.613〜0.617）、1750秒 0.449（前 0.438〜0.460）で、前の幅の中。
- 参考（変更前からある性質）：初めの gain 0.5 が小さすぎる地点では、上がる途中に上げられず、保持に入ってから 0.004/s でゆっくりしか上げないので、保持の前半は岸の水位が H より低い（模型で H=5 に対して最小 4.2m）。今回の差分の問題ではないが、「浅く出る」向きの仮定なので、別に見る価値がある。

### D. 試験の式
- **T4**：Thacker（1981）の軸対称の放物面の解として正しい。底 z=−h0(1−r²/a²)、η=h0{√(1−A²)/(1−A cos ωt) − 1 − (r²/a²)[(1−A²)/(1−A cos ωt)² − 1]}、ω=√(8gh0)/a。A は (0,1) の自由な定数で、A=(a⁴−r0⁴)/(a⁴+r0⁴) は「t=0 の水際の半径が r0」となる選び方（水深 h=h0[√(1−A²)/c − (r²/a²)(1−A²)/c²] が r²=a²c/√(1−A²) で0、t=0 で (1−A)/(1+A)=r0⁴/a⁴ を入れると r=r0）。SWASHES の η0 を使う形 A=((h0+η0)²−h0²)/((h0+η0)²+h0²) とも同じ解。初期の流速0（u ∝ sin ωt）、摩擦0、造波帯なし（sea=0）、近岸帯なし（coastIdx は角の1セル・乾き）で、条件は解に合っている。水際の最大半径は約188m で、箱 ±256m に当たらない。誤差は `s.time`（実際に進んだ時刻）で解析解を出しているので、時刻のずれは入らない。
- **T2**：Ritter の h=(2c0−x/t)²/(9g)、深さ hc の線 x=t(2c0−3√(g hc))、x=0 で 4/9 h0、いずれも正しい。先端の位置の量子化は ±0.5m（先端まで約54m）で約1%。
- **T1**：質量の基準を 1e−5 → 1e−6 に締めたのは設計書どおり。
- **T5 が試していないこと**：中-4 に記した。
