### 1-2. 継ぎ目（clipSeg・結び直し）

- clipSeg（Liang–Barsky）は、手で読んでも、4地点・10タイル以上での実行でも、誤りは見つからなかった。`p === 0` の平行線、`t0 > 0` / `t1 < 1`（切り落としの印）も正しい。各タイルは自分の正方形だけを出すので、緩衝帯による二重は無い（重複辺の読み飛ばし `link` の `adj[a].some` が働いた回数は 0）。
- **結び直しの実測（8地点：5地点＋継ぎ目の角3）：結び直しで結ばれた組は 0本。** 理由は、GSI の線が**タイル境界ちょうどに頂点を持つ**ため（境界上の頂点が各地点で 260〜1224個）、隣のタイルの同じ点と 0.25m 丸めのキーが完全一致して統合されるから。切り落としで作られた端点（「切り落とし端点」13〜50個）は、すべて隣のタイルの点と同じキーで統合済みで、次数1で取り残された端点は 0。継ぎ目の3m以内の次数1ノードは、結び直しの前後とも同数（名古屋1→1、高知2→2、尾鷲1→1、串本0→0、善進0→0）で、本当の行き止まり。**継ぎ目で道が切れている箇所は見つからなかった。**
- 0.25m 丸めの統合：タイル格子の1目盛りは約0.5〜0.6m（ズーム14・4096分割）なので、同じタイル内の別々の頂点が誤って1点になることは無い。交差点は、隣り合う線が同じ頂点を共有するので1点になる（別実装でも同じ結果）。
- 立体交差：交差点で線が分割され、立体交差では頂点が共有されないので、**立体交差の誤接続は起きない**（2703 橋・高架の中ほどのノードに地上の道がつながる例は、別実装との一致から見て無い）。コメントの「立体交差が同じ点でつながって見えることがある」は、実際には起きていない（安全側の記述）。
- 結び直し（1.6m）の誤接続の危険：結び直しの対象は、「切り落としで作られた端点」だけ。8地点で結んだ組が 0本なので、実害は観測されない。理論上は、タイル境界をまたぐ1.6m未満で並行する別の道を結ぶ恐れがあるが、観測値は 0。実質的に**到達しない処理**で、試験もされていない（軽微 L1）。
- 連結成分：名古屋 7（最大 76.9%）、高知 4（90.2%）、尾鷲 12（97.3%）、串本 7（93.9%）、善進 2（99.7%）。主ネットワーク以外の成分は、範囲の縁（x または z が ±1150m 付近）で切れたものか、孤立した小路。主ネットワークの行き止まりと8m以内に近づく別成分は、範囲の縁の外側または2〜11ノードの小成分のみで、範囲の内側に「つなぎ忘れ」は見つからなかった（名古屋の243ノードの成分は、x=1243m＝範囲外、主網まで8.3m）。出発点・全行き先は、すべて最大成分に入っていた。

### 1-3. 経路の線の連続性

- 経路は、`prev` の鎖をたどって辺ごとに作られるので、**構造上、線は切れない**。隣り合う点の間隔の最大値（出発点から道への最初の脚と、道から行き先への最後の脚を除く）：名古屋 136m、高知 145m（高い所 H=15 では 294m）、尾鷲 95m、串本 49m（H=18 では 151m）。どれも、頂点の少ない長い直線の辺（実在の一本道）で、断絶ではない。

## 2. 最短の道のり（shortestPaths・snapToGraph）

- ダイクストラ法とヒープ（上げ下げ・遅延削除 `d > dist[u]`）は正しい。到達不能は `Infinity`、使う側は `Number.isFinite` で判定していて正しい。計算時間は、尾鷲（3926ノード）で 2.8ms。
- **到達不能の取り扱い**：`snapToGraph` を、**`shortestPaths` の前**に全部終えているので、差し込んだノードも探索に入る（順序は正しい）。

### 指摘 M1（中）：出発点と行き先が同じ道の区間にあるとき、道のりが長く出る

- 場所：src/data/roads.js:108-124（`snapToGraph`）、呼び出しは src/route.js:25-28。
- 原因：辺を分割するとき、**元の a–b の辺を残したまま**新しいノードを a と b にだけつなぐ。出発点を差し込んだあと、同じ元の辺に行き先を差し込むと、近さが同じ（共線）で、**先に見つかる元の辺**が選ばれる（`d < best.d` が厳密比較のため、同点なら先勝ち）。行き先ノードは出発点ノードと直接つながらず、a か b を回る遠回りになる。
- 再現（実測）：尾鷲の長さ 82.9m の辺で、出発点を 0.3、行き先を 0.6 の位置に差し込むと、道のり 74.64m（正しくは 24.88m。3倍）。同じ辺の組を300通り試すと 288通り（96%）で 0.5m 以上長く、最大で 64.7m 長く出た。
- 実際の頻度（出発点を各地点の周り ±300m にばらつかせ、行き先は実データの5か所、150通り×5か所、約3700組で、辺を分ける修正版と比べた）：名古屋 2/705、串本 1/745（最大 55.8m）、高知・尾鷲・善進 0。**およそ 0.1%。** 誤りの向きは「長く出る」（安全側）だが、近い行き先が、順位から落ちたり、道のりが 500m を超える印が付いたりしうる。地図の線は、遠回りで描かれる。
- 直し方：分割のとき、元の辺（`adj[a]` から b、`adj[b]` から a）を取り除く。上の検証で使った修正版（`snapFixed`）は、この方法で正しい値を出した。
- 判定：実害の頻度は低く、誤りの向きも安全側なので「重大」とはしないが、確実に直るので修正を勧める。

### 道から離れた分の足し込み

- `road = dist + start.d + sn.d`：出発点と行き先から道までの直線距離を足す。「道のり ≥ 直線距離」の検査（after_report.json の `roadNotShorterThanStraight`）と矛盾しない（すべて道のり ≥ 直線）。妥当。ただし、`start.d` は最大 150m、`sn.d` は最大 120m で、**道の網に載らない距離が最大 270m 含まれうる**。画面は「道のり約○m」としか書かず、道を外れる距離を区別しない（軽微 L3）。

- 高い所の判定はノードごとで、辺の途中は見ない。長い直線の辺（294m など）では、基準を超える地点より手前に遡れず、**道のりが最大で辺の長さ分、長く出る**（高知 H=15 の 294m の辺）。安全側。

### 軽微 L6：串本 H=10・H=18 の地点は徒歩道（2721）の上

## 4. 「地面の標高」と海の高さの比較（brief.js の routeHtml）

- 標高の読み取りは、施設の代表点（`s.lat, s.lon`）の双線形補間。`e < H` のとき「海の高さより低い場所です」、それ以外は「海の高さ H 以上」。**NaN は null で「取得できませんでした」**になり、低い・高いの判定には入らない（正しい）。
- 例：名古屋 1.0／0.6／1.6m（H=5 では「低い」）、善進 −0.4m（ゼロメートル地帯と整合）、高知 A 4.8m（H=15 で「低い」）、尾鷲 A 24.7m。

### 指摘 M3（中、M2 と同根）：境界付近の判定の扱い

- 場所：src/brief.js の `routeHtml`（`r.elev < H`）。
- 10mメッシュの誤差（尾鷲で最大 4.5m、串本で 3.9m。上の表）に対して、`e ≥ H` を、「通常の色」の「海の高さ H 以上」とだけ書く。誤差内の差でも「低い」と「以上」が分かれ、「以上」の側に誤った安心感を与えうる。高知 A（4.8m）は H=5 のとき「低い」だが、H=4.7 なら「以上」で、0.1m の差で見出しが変わる。
- 直し方：H±1m（または誤差帯）は「ほぼ同じ高さ。標高は数mずれることがあります」のような中立文にする。「以上」の文に「標高は10mメッシュの目安」を添える。

## 5. 再計算・古い結果の混入・通信失敗・キャッシュ

- **古い結果**：`loadRoute(lat, lon, c, my)` は、待ったあとに `if (my !== token) return;` で捨てる（brief.js:270）。`update()` で `token++`、`routeSel = null`、`cur = {…route: null}` に差し替え、`drawRoutes()` で線も消す。素早く切り替えた場合の混入は無い（読んで確認）。`setWave` は `cur.route` が `ok` のときだけ動く。経路が未完のときに海の高さが変わっても、完了時の `computeHighs()` が `getH()`（その時点の値）を使うので、取りこぼさない。
- **海の高さ変更**：`#H` の `input` と `setH()` の両方でデバウンス 350ms の `brief.setWave()`。`setH` 以外で `#H` の値を書く箇所は無い（grep で確認）。`computeHighs` は `rt.H` を持ち、`part('route')` は `cur.route.H` で描く。行き先を選んでいて消えた場合は `routeSel = null`。正しい。計算時間は 0〜4ms で、デバウンスは不要なほど軽い。
- **通信失敗と「道なし」の区別**：`loadRoadGraph` はタイル取得の失敗（404以外）を `failed`、404のみ・全タイル空を `empty`→`noroad` と区別する。`fetchOk` は 404 だけを `null` にし、他は throw。画面の文も「取得できませんでした」と「近くに道のデータがありません」で分かれ、after_report.json の offline_pc で確認されている（`offlineSaysFailed`・`retryWorks` が真）。
- **キャッシュ**：roads.js の `cache` は、失敗した Promise を `p.catch(() => cache.delete(url))` で消す（再試行できる）。404 の `null` は持つ（妥当）。evac.js も同様。標高タイル（`loadDemMosaic`）は、roads と違い**キャッシュ無し**で、毎回取る（ブラウザの HTTP キャッシュ頼み。GSI の応答は `last-modified` のみで `cache-control` 無し＝ヒューリスティックなキャッシュ）。

### 軽微 L7：タイルの解析失敗が黙って捨てられる

- src/data/roads.js:70 の `catch { return; }`（壊れた pbf）は、その1枚を道なしとして**黙って**扱う。通信の失敗とは別扱いなので、1枚だけ壊れた場合、道がつながらないように見える（「道がつながらなかった場所」の表示に化ける）。実害は低い。

## 6. データの利用条件・出典・気象庁の文

- **気象庁の原文（WebFetch で確認）**：「一般的に、津波の「遡上高」は海岸付近での「津波の高さ」の２倍〜４倍に達することが多く、Ｖ字谷のような特殊な地形の場所ではさらに高くなることがあります。」（前の文で、発表される「津波の高さ」は海岸付近の高さで、遡上高とは異なると説明）。09 の転記と一致する。
- 画面の文（routeHtml）：「気象庁によると、津波が陸をかけ上がる高さは、海岸での津波の高さの2〜4倍に達することが多いとされています。」→ **意味は原文を超えていない**（「多い」と書き、断定していない）。

### 指摘 M4（中）：原文の後半「V字谷ではさらに高くなる」が省かれ、「2倍」の行が目安に見える

- 場所：src/brief.js の routeHtml の最後の注意文。
- 画面は「海の高さの2倍（○m）より高い所」の行を出す。原文は「2〜4倍に達することが多い」で、「4倍」と「特殊な地形でさらに高く」が上限を示す。画面の文は2〜4倍と書くが、**2倍の地点が十分ではないこと、地形によってはそれ以上になること**は書いていない。尾鷲・串本のような谷・入り江の地形では、2倍の地点で足りないことがある。
- 直し方：「2〜4倍に達することが多く、V字谷のような地形ではさらに高くなることもあります」と原文どおりにし、2倍の行にも「これで十分とは言えません」を添える。
- 補足：設計（3節）が掛け算の「2倍」を採るのは実装者の判断で、気象庁の文は「2倍まで」ではなく「2〜4倍に達することが多い」と書く。

### 軽微 L8：出典・利用条件

- 道：画面の出典は「国土地理院ベクトルタイル提供実験の道路中心線と、地理院タイル（標高タイル）を加工して作成」。README が求める「国土地理院ベクトルタイル提供実験」の明示、加工の旨は満たす。09 が推奨した「**実験提供である旨・基本測量成果ではない・内容が変わりうる**」の免責は、画面にも設計にも**無い**（文は「地図にない細い道…は入っていません」のみ）。法的判断ではないが、09 の推奨との食い違い。
- 標高タイル：09 には、標高タイル（`dem_png`）の**利用条件・精度・出典表記の一次情報の確認が無い**（grep で DEM 関連の記載なし）。画面は「標高タイル」を出典に挙げるが、データの出典名（基盤地図情報数値標高モデル）や精度は示さない。国土地理院の一覧ページ（https://maps.gsi.go.jp/development/ichiran.html）はこの確認では全文を読めず、**標高タイルの精度・条件は未確認**。補強するなら、09 に1節を足す。
- 津波浸水想定の想定値や PLATEAU は、この機能では使っていない（出典不要）。
